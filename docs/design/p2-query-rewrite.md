# P2 查询改写（LLM 多查询）设计

> v0.9.7 已升级为“发送前 QueryPlan + 软 AND 覆盖度 + 原问题兜底”，见 [query-plan.md](query-plan.md)。本文保留早期多查询改写设计。

> v0.7.3。目标：把自然语言问题扩成 2–3 个检索式，提升「同义/换个说法」的召回；默认关，失败自动回退。

## 1. 范围（v0.7.3 更新：广播改写）

- 作用于**提问端**：
  - 本机搜索（`/api/search`）；
  - 随手问：**广播前**先改写，选第一条精炼查询作为 `text` 发给所有在线节点；
    - 原问题保存在 `question` 字段，仅用于展示与 AI 综合；
    - 被搜索端用精炼词做 BM25/向量召回（不调 LLM、不增加请求数）；
    - 本机节点也直接用精炼词检索（避免二次改写）。
- 代价：每次提问多一次 LLM 调用（约 1–3s，提问端）；失败/超时回退原文。

## 2. 触发与安全边界（v0.7.4）

- **原查询有强命中时完全不改写**（本地搜索与随手问广播一致）：不调用 LLM，结果与关闭改写相同，也避免 2–3 秒额外延迟；
- 只有原查询**没有强命中**时才请求 AI 改写；
- 改写结果在本地搜索中**只追加、不重排**原查询结果（base 永远在前）；
- 广播候选只接受有意义短语（去掉"的/了/是"等边界字、过短片段、问句词），且原查询有强命中时绝不替换；
- 多有效词的问题优先「全词 AND」，避免 3-gram 片段劫持（修复「怎么模拟网络丢包」召回错误）；
- 含英文/技术术语的查询做术语锚定（vector/hybrid 命中例外）。

## 3. 广播选择策略（v0.7.3 实现）

改写后不直接拿第一条广播，而是用本机检索做一次"候选试跑"：

- 候选 = 原问题的短语候选（去掉「请/说明/怎么/一下」等）+ AI 改写结果 + 原问题；
- 每个候选在本机跑一次 top-5，按「是否有强命中、标题是否包含原问题词、命中数」打分；
- 接近平手时优先更短、且是原问题子串的候选（更聚焦，对旧版本节点也更稳）；
- 只有明显更好才替换原查询，否则保持原查询——避免改写把结果改差。

原问题始终保存在 `question` 字段，用于展示与 AI 综合；节点只收到精炼后的 `text`。

## 4. 流程

```
原查询 → 原查询检索（BM25+向量+P0.5）
       → [可选] LLM 改写 2–3 条检索式 → 各自检索
       → RRF 合并（同文档/同块去重，1/(60+rank)）
       → 仅改写命中的新结果标 route="expanded"
       → P0.5 分层 / rerank / 展示
```

失败/超时（默认 4s）/未配置 AI → 直接返回原查询结果；改写结果缓存 1 小时（LRU 128）。

## 5. 配置（query.json）

| 字段 | 默认 | 说明 |
|---|---|---|
| enabled | false | 总开关 |
| max_queries | 3 | 最多改写条数（1–5） |
| timeout_s | 4.0 | 单次 LLM 超时 |

API：`GET/POST /api/query/config`；设置页「查询改写」面板显示 AI 是否已配置。

## 6. 提示词（可自定义）与解析

默认系统提示词（设置页可直接编辑，清空恢复默认）：

```text
你是搜索查询改写器。请从用户的问题中提取 1-3 个检索式，每个检索式只保留与问题相关的关键词；不要问句、不要解释、不要编号，一行一个。保留专有名词和英文术语原样（如 fcntl、nginx），不要添加“使用方法/用法/介绍/相关/测试”等泛词，不要引入问题中不存在的新事实。
```

- 保存位置：`query.json` 的 `system_prompt`；空/未设置时用内置默认；
- API：`GET/POST /api/query/config` 返回/接受 `system_prompt` 与 `default_prompt`；
- 解析：兼容 JSON 数组/编号行/普通行，去编号、标点、空行，过滤与原文相同、长度 <2 或 >40 的行，去重后截断。

## 7. 测试与验收

- 单测：解析、配置 roundtrip、缓存命中、RRF 合并与 expanded 标记；
- 线上：开启后搜索延迟增加一次 LLM 调用（约 1–3s），结果召回应提升；关闭后无影响；
- golden set 回归仍要求 recall@5 不下降。

## 8. 推荐组合（基于 2×2 实测，见 docs/review/p2-ab-evaluation.md）

| 场景 | 组合 | 说明 |
|---|---|---|
| 4C8G / 内存敏感、有 AI | **rewrite 开 + 本地 rerank 关** | 内存约 200MB；recall +7pp；延迟 +2.4s/问 |
| 有内网 rerank | **rewrite + HTTP rerank** | 本地零模型；质量最佳 |
| 质量优先、内存宽裕 | rewrite + 本地 rerank | 峰值约 740MB；nDCG/MRR 最高 |
| 离线 / 无 AI | base（按需本地 rerank） | 本评估中 rerank 单独无增益，默认关 |
| 纯搜索、低延迟 | base 或 base + HTTP rerank | 毫秒级 |

## 9. 已知边界

- 改写质量依赖模型与提示词；小模型可能生成泛化查询；
- 每次开启状态下的搜索多一次 LLM 调用（成本/延迟），默认关；
- 跨节点改写广播未做（会放大请求量），后续可做「只改写并广播 1 条最佳查询」的轻量方案。
