## 1. 产品定位与命名

**一句话**：让个人笔记里的知识能被团队搜到，而知识永远留在每个人自己的电脑上。

**命名由来**：典出「凿壁偷光」——在墙上凿一个小孔，借邻居的烛光读书：不搬灯、不拆墙，只借光。对应产品哲学：知识（灯）留在本地（邻居家），隐私边界（墙）不动，只通过索引（小孔）让答案（光）透过来；呼应三体「破壁者」的意象，但比「推倒墙」更克制。英文名 ChiselWall。

**产品原则**：
1. 知识不出本机：原文只在用户明确请求查看时由源节点回传；
2. 中心不存知识：relay 只做在线状态、广播、回传与限流，不落盘任何笔记内容；
3. 零迁移：不改动、不复制用户的笔记文件，不改变记录习惯；
4. 低打扰：所有对他人设备的访问都有资源预算（§12）；
5. 隐私默认：排除即完全不可见（§7）。

## 3. 总体架构

三部分：Relay（中心）、Node Agent（每台电脑）、Web UI（随 agent 提供）。

```text
                         [公司内网]
  ┌───────────────────────┐                ┌─────────────────────┐
  │ Relay（常开机器）      │  TCP/WS (TLS)  │ nats-server         │
  │ 只路由：presence /    │◄──────────────►│ 核心模式，无 JetStream│
  │ 广播 / 回传 / 限流     │                │ 每用户 token 鉴权    │
  └───────────────────────┘                └─────────────────────┘
         ▲   ▲   ▲
         │   │   └───────────────────────────┐
  ┌──────┴───┴────────┐                ┌──────┴────────┐
  │ Node Agent A       │                │ Node Agent B  │   （每台电脑一个）
  │ ├─ Connectors      │                │ ……同左         │
  │ ├─ Indexer         │                └───────────────┘
  │ ├─ Searcher        │
  │ ├─ Responder       │
  │ └─ Web UI(127.0.0.1)│
  └────────────────────┘
```

**消息流（随手问）**：提问 → agent 生成 qid 广播 → 各在线 agent 限流后本地检索 → top-k 片段回传 → 提问端 deadline 内聚合去重排序 → 展示 →（可选）AI 综合带引用作答。

**为什么是 NATS 核心模式**（调研 01 结论）：核心 NATS 无持久化、at-most-once、只投递给发布时刻在线的订阅者——恰好等于「中心只分发、不存知识」；原生请求-回复 + 超时 + no-responders 语义直接支撑广播问答；自带慢消费者切断与 token 鉴权；单二进制部署。备选：自建 WebSocket relay、MQTT（请求-回复需自己约定 correlation id）。

## 4. 消息协议（NATS Subjects 与消息体）

| Subject | 用途 | 模式 |
|---|---|---|
| chisel.presence.<user> | 心跳/在线声明 | 发布；中心内存维护路由表 |
| chisel.query.broadcast | 问题广播（全员组，v1） | 发布给全体在线者 |
| chisel.query.<group>.broadcast | 组内广播（M4 起） | 只发给该组在线成员；提问默认广播到提问者所在组 |
| chisel.answer.<asker>.<qid> | 结果回传 | 请求-回复（queue group 防重复） |
| chisel.fetch.<node> | 请求完整文档上下文 | 请求-回复 |

消息体（JSON）：

```text
QueryMsg   { qid, asker, text, deadline_ms, topk, mode }
HitMsg     { qid, node, hits: [ { doc_id, source, title, snippet, score, rel_path } ] }
FetchMsg   { qid, doc_id, max_chars }
FetchResp  { qid, doc_id, text, truncated }
```

超时语义：节点端带 deadline（查询预算），到点回部分/空结果；提问端整体 deadline 收口；无订阅者时 NATS 立即回 no-responders，避免干等。实现注意（调研 03）：nats-py 的 request() 只收首个回复，广播聚合必须用 subscribe + 按 qid 收口，deadline 后取结果集。

## 5. 本地索引设计

**存储**：单文件 SQLite（chiselwall.db），内含：
- docs 表：doc_id、connector、path、title、mtime、size、hash、状态、是否排除；
- chunks 表：chunk_id、doc_id、seq、text（分块原文）；
- FTS5 虚拟表 chunks_fts：主列 unicode61（英文/数字）+ content_jieba 影子列（jieba 切词后空格连接）；
- 可选 trigram 兜底表（任意 ≥3 字子串，覆盖代码/缩写/短词）——M2 验收实测：无条件写 trigram 空间达原文 755%（AC-03-11 不达标），已定：**默认关闭、可配开启、开启时仅 <100K 字符小文档写入**（评审 F2）；
- 可选 vec0 向量表（sqlite-vec，512 维 int8），语义搜索开关控制。

**中文检索方案**（调研 02 结论）：入库时 jieba 切词写入影子列；查询时同样切词组合为 FTS5 短语查询；用 bm25() 排序；短词/子串走 trigram 兜底。思源自身即用 SQLite+FTS5 做全文检索，佐证该引擎足够支撑笔记级中文搜索。社区实测参考（docs/research/03）：中文查询 unicode61 直接命中 0%、trigram 65%、L1 查询扩展 82%；jieba 影子列 + trigram 兜底的 SQL/路由/snippet 骨架可直接参照实现。

**Chunk 策略**：按标题/段落边界切分，每块 500–800 字、前块重叠 50 字；超大文件截断（默认单文件文本上限 5MB）；每文档 chunk 数上限（默认 2000）防异常文件。

**增量索引**：watchdog 监听（Linux inotify / Windows ReadDirectoryChangesW）→ 防抖 3–5s → (mtime, size, hash) 校验真正变更 → 单线程 worker 按 rowid 增删改；启动时全量校验一次；索引在空闲且 CPU 低负载时推进，收到广播查询时检索优先、索引让路。

**上下文片段**（用户问：命中一两个词怎么带上下文）：因为按 chunk 存了原文，命中后定位命中词在 chunk 中的位置，向前向后各取约 150 字，首尾加省略号，返回约 300 字带高亮的上下文片段；多个命中取得分最高片段。不依赖 FTS5 snippet()（其分词输出对中文不友好），自己做窗口截取，效果更可控。

## 6. 连接器设计

统一接口（Connector Protocol）：

```text
list_docs() -> [{doc_id, title, rel_path, mtime, size, format}]
read_doc(doc_id) -> text | 结构化块
watch() -> 文件事件流
formats() -> 支持的扩展名
default_excludes() -> 默认排除 glob
```

**v1 实现**：
- DirectoryConnector：txt（charset 检测）、md、docx（python-docx）、xlsx（openpyxl，含多 sheet）、pdf（pypdf，扫描件跳过）、csv；.doc/.xls 旧格式跳过并提示；加密文件跳过；
- ObsidianConnector：vault 即 md 目录，复用 DirectoryConnector，默认排除 .obsidian 配置目录；
- SiyuanConnector：v1 必须支持。直读工作空间 data/ 下 .sy 文件（Lute AST JSON，官方规范公开、Spec 2-6、IAL 与 base64 约定，见调研 03），纯 Python 树遍历自写解析器（社区无成熟第三方库），按 spec 版本兼容；官方 CLI「siyuan export md」可作兜底通道；加密笔记本密文不可读（跳过并记录）；思源运行时可通过本地 127.0.0.1:6806 内核 API（Token 鉴权）做增强（实时块/跳转）；解析失败的文档跳过并记录，不阻断整体索引。

**预留接口（v1 后）**：NotionConnector（官方 API，游标分页 + 3 req/s 限流，定期拉取导出→本地索引）、YoudaoConnector（youdaonote-pull 非官方导出，标注失效风险）、LinkConnector（论坛/wiki/CMS/网页链接，抓取+更新策略，对应「共享链接」需求）。

## 7. 排除规则与隐私

- 挂载：添加目录或单文件；排除：单文件、整目录、通配符（glob）规则；
- 默认排除：隐藏文件/目录、.git/.svn、node_modules、.obsidian、临时文件（~$、.tmp）、二进制文件、超过 20MB 的大文件（阈值可配）；
- 可见性：被排除内容不进索引、不参与任何应答、全文获取也不可得；
- 结果回传内容：命中片段（约 300 字）+ 出处（用户昵称 + 文档标题 + 相对路径）+ 得分，不含其余文档内容；
- 全文查看：提问者点击结果 → chisel.fetch 向源节点请求完整段落/全文，源节点限流后返回（能被搜到即可被查看；敏感内容请用排除规则）；
- 后续版本预留：用户级黑名单、某文件「只出标题不出正文」分级。

## 8. 随手问（广播问答与聚合）

1. UI 输入问题 → agent 生成 qid（含 deadline，默认全流程 5s 收口）；
2. relay 广播 chisel.query.broadcast；
3. 各在线 agent：token bucket 限流（默认每来源 1 问/5s）→ 本地检索（关键词；开启语义的节点混合向量）→ top-k（默认 8）片段回传；
4. 提问端聚合：按 doc_id/近似重复去重 → 得分排序（节点间按命中数/得分加权）→ 总数上限（默认 60）→ 展示：在线人数、各节点响应状态、结果列表（片段高亮 + 出处）；
5. 点击结果：查看完整上下文（fetch）；若命中来自本机自己的索引，可直接在文件管理器中定位原文件（他人机器上的文件不可定位，只能查看其回传内容）；
6. 无 AI 配置时到此为止；有 AI 配置时进入 §10 综合。

## 9. 随手记 UI（侧边栏式）

参考 DSH 侧边栏的「集中管理」思路（不照搬、不依赖）：

- 左侧导航：随手记 / 随手问 / AI 问答 / 设置；
- 随手记页：挂载列表（目录树）——添加/移除目录或文件；右键排除（单文件/目录/通配符）；索引进度与文档统计（已索引 N 篇、待处理、失败列表）；排除规则面板；笔记分组（自定义分组归类，按组筛选/统计/批量排除，§15.6）；
- 右侧/详情：文档预览（只读，标注是否参与共享）；每个文档两个操作——**「打开所在位置」**（在文件管理器中定位并高亮选中该文件：Windows 用 explorer /select,path；Linux 用 xdg-open 打开所在目录或 DBus org.freedesktop.FileManager1 ShowItems 高亮）与**「直接打开」**（用系统默认程序打开原文件，不改动原文件）；随手问结果若命中本机文档，同样提供这两个操作（他人机器上的文件不适用，见 §8）；
- 设置页：relay 地址、昵称、token、AI 配置（provider/base_url/model/key）、语义搜索开关、限流参数。

## 10. AI 入口设计

**主形态（v1）：提问者侧 RAG 综合**
聚合结果 top-N（默认 20 片段）→ 按模型上下文长度拼接 → LLM 生成带引用编号的答案（引用对应结果列表序号，可点开看片段原文）。Provider 抽象走 OpenAI 兼容客户端：DeepSeek API（base_url=https://api.deepseek.com）或 Ollama（http://localhost:11434/v1）；未配置 AI 时 UI 只展示片段列表。

**查询增强（可选开关）**：提问者侧先让 LLM 把问题改写成 2–3 组关键词查询再广播，提升关键词召回。

**节点侧本地 AI（预留，v1 不做）**：节点在自己的命中片段上用本地 LLM（Ollama）生成短答案再回传——隐私最强（内容不出本机）。但全员开启 = 每次提问所有在线节点都跑一次 LLM，成本与延迟不可控，故默认关闭、接口预留。

**Embedding（向量语义搜索，可选、默认关闭）——普通电脑带不带得起？**
- 向量检索必须先用 embedding 模型把文本转成向量。默认方案：本地跑 bge-small-zh-v1.5 的 ONNX int8 量化模型（文件约 30MB、推理常驻内存约 100MB、CPU 单条约 5ms、限 2 线程）——普通办公电脑（4C8G 及以上）完全带得动，且仅索引期/查询期占用 CPU（空闲调度）；
- 备选：接 OpenAI 兼容 embedding 服务（Ollama /api/embed 或第三方云服务）。注意：DeepSeek 官方 API 目前没有 embedding 端点；
- 每台机器自愿开启、默认关闭；关闭不影响关键词搜索。

**对端搜索是否用 AI？**：默认不用。对端 = 纯本地检索引擎（关键词 BM25 / 可选向量 ANN），毫秒级、轻资源；LLM 只在提问者自己侧跑一次做综合。这样每次提问全局只有一次 LLM 调用，成本与延迟可控。

## 11. 安全与鉴权

- Relay：nats-server 开 TLS（内网可自签证书分发）+ 每用户独立 token + 按 subject 授权（只能发布 chisel.query.broadcast、订阅自己的 chisel.answer.<me>）；中心只维护「用户→在线状态」内存路由表（元数据，无知识内容）；
- Node：Web UI 与本地 API 只监听 127.0.0.1 + 随机 token；配置与索引库在本机用户目录；
- 进阶（后续）：mTLS、NKeys、跨部门 NATS accounts 隔离。

## 12. 资源保护（不把同事电脑打满）

| 机制 | 做法 |
|---|---|
| 双向限流 | 每来源用户 token bucket（默认 1 问/5s），同时限「接受他人查询」与「本机外发」 |
| 时间预算 | 每查询 deadline（节点默认 800ms），到点回部分/空结果，绝不排队 |
| 并发上限 | 同时处理的查询数硬上限（参考核数），参考 Netflix concurrency-limits 用延迟反馈自适应 |
| 背压 | 有界队列 + 丢新策略；NATS 服务端慢消费者切断兜底 |
| 索引让路 | 单线程 worker、进程低优先级（psutil）、空闲调度、批事务；检索优先于索引 |
| 结果限量 | 每节点 top-k（8）、全流程聚合上限（60） |
| 达标线（v1 目标，4C8G 参考机） | 空闲 CPU<1%、RSS≤200MB；索引期 CPU≤50%（整机口径，单线程 worker 实测=单核脉冲即整机 25%）、峰值内存≤1GB；检索 P50≤30ms/P95≤100ms；索引库体积≤索引文本 500%（中文词级实测口径：chunks 原文~100%+FTS 索引~300%；原 50% 为英文词级口径、中文结构性不可达，已废弃） |

## 14. 风险与开放问题

- NATS 单点：中心宕机即失联（知识仍在本地、只是暂时搜不到）；后续可做双机热备/集群；
- 思源 .sy spec 版本差异：先支持常见版本并做兼容解析，失败跳过并记录；需要你提供几份真实工作空间样本用于测试；
- 有道/Notion：依赖云接口与账号授权，有失效风险，v1 后按需做；
- 中文搜索精度：jieba 词库 + 可加部门自定义词典；上线前用真实笔记做一轮检索质量抽样；
- DeepSeek API 无 embedding 端点：语义搜索默认走本地模型，已规避；
- 内网自签 TLS 证书分发：安装包内置证书或首启自动信任，需运维配合；
- 待确认：内网模型的接口形态（是否 OpenAI 兼容、有无 embeddings 端点）；同事电脑配置基线（按 4C8G 假设）；Notion/有道在部门内的实际使用人数（决定连接器优先级）。人数已确认：100 起步、目标千人级（§15.4）。
- M2 遗留（挂起至 M6 复查）：「直接打开」在 harness 托管实例中用户点击后无可见窗口。证据更新：用户关闭全部 VS Code 后重试仍无窗口；服务端 200、os.startfile 已执行；同进程 Popen(记事本) 却可见——推断 ShellExecute 路径在该托管上下文静默失效、CreateProcess 路径正常。修复候选（M6 执行）：_windows_open_file 改为用解析出的关联命令走 Popen([exe, path])，必要时加窗口激活；同时保留 open-with 应用内兜底。用户已明确指示：先记录、后续修复，不阻塞 M3。

## 15. 第二轮评审增补（用户反馈落案）

### 15.1 Notion / 有道云笔记的本地数据说明

- 两类都是「云端型」笔记：正文权威存储在服务端，本地只有缓存，不能像思源 .sy 那样当作可靠笔记文件直接索引。
- Notion：桌面端（Electron）本地维护一个 SQLite 缓存用于离线（官方称「尽力而为」：不保证哪些页面被缓存、保留多久，格式非公开稳定）。社区已有直接读取该缓存的项目（notcrawl、notion-cache MCP），所以「内网离线也能看部分内容」是可能的；官方 REST API 需用户授权 token + 3 req/s 限流；官方也支持导出 Markdown/HTML zip。
- 有道云笔记：本地缓存加密、私有格式；无官方导出 API；开源 youdaonote-pull 走 Web 接口把笔记（Xml/Json）拉下并转 Markdown（非官方、随改版可能失效）。纯内网无外网时，有道云笔记本体也无法同步（云产品）。
- v1 实用路径（零开发、立即可用）：用官方导出功能把笔记导出为 md/html 放进某个目录 → DirectoryConnector 挂载索引。
- 连接器路线（后续，按优先级）：① Notion 本地 SQLite 缓存读取（省事但官方不保证、格式可能随版本变化，标注不稳定）；② Notion 官方 API（稳定，需授权与外网）；③ 有道 youdaonote-pull 导出（非官方，风险标注）。无论哪条，内容都只进本机索引，中心不过手，不违反产品原则。

### 15.2 随手问：增量展示 + 收口综合（采纳；经产品分析确认有必要）

- 产品分析结论：有必要。分布式响应天然乱序到达（快节点约百毫秒、慢节点逼近 deadline），整体收口默认 5s——干等白屏体验差；先到先显示把等待变成可见进度，感知延迟大幅下降；实现成本低（与请求-回复 + deadline 模型天然契合）。
- 增量阶段：结果到达即渲染（UI ~100ms 节流合并批量，避免抖动）；「有效性分析」用规则打分（BM25 分数、命中密度、长度合理性）过滤明显低质项，折叠为「低相关 N 条」；顶部显示「已响应 x/n · 在线 n」进度。
- 收口阶段：deadline 到期或全部响应后统一去重（doc_id/近重复）与重排序；配置 AI 时生成带引用编号的综合答案；UI 在「增量结果」与「综合答案」间切换。
- 成本红线：增量阶段不调用 LLM（每条结果跑一次 LLM 不划算）；LLM 仅在收口时跑一次综合。

### 15.3 内网模型接入（公司内部有内网模型）

- provider 抽象走 OpenAI 兼容端点，内网模型只需配置 base_url + model + key 即可接入（M5 直接用，不必依赖 DeepSeek API）。
- 若内网模型提供 OpenAI 兼容 /embeddings 端点，向量语义搜索可改为走内网服务，省去每台机器本地跑 embedding 模型。
- 待确认：内网模型的接口形态（是否 OpenAI 兼容、有无 embeddings 端点）。

### 15.4 千人级演进（当前 100 → 目标 1000）

- 架构判断：单机 NATS 撑 1000+ 长连接与广播无压力（生产级消息系统），核心模式无持久化使中心负载极低；节点 agent 设计不变（每节点只服务自己的索引与查询预算）。1000 人不是架构变化，是参数与组织变化。
- 演进项（subject 已预留）：① 分组广播 chisel.query.<team>.broadcast——按部门/小组分域，避免全员广播轰炸；② 聚合分层——组内先聚合再跨组汇总，控制提问端结果总量；③ 聚合上限/去重参数随规模调优；④ relay 双机热备（§14 单点风险）；⑤ 用户级黑名单与分组可见性。
- v1 只实现全员一组广播，subject 命名预留分组粒度。

### 15.5 聚合漏斗、AI 上下文预算与多会话（第三轮反馈落案）

**问题**：百人/千人广播时，各节点返回混杂（无命中/低相关/高相关），聚合怎么做、会不会打爆 AI 上下文。

**四层漏斗**（以 1000 在线、每节点 top-k=8 为例，上游最坏 8000 条候选）：

- L1 节点侧过滤（发出前）：无命中的节点静默不回（UI 用「在线 n · 已响应 x」表达，收口时其余记为未返回命中，避免千人规模空确认消息翻倍）；低于分数阈值的命中不发；空片段不发。
- L2 提问端去重与共识：相同 doc_id 去重；近重复检测（shingle/MinHash 相似度）合并不同人持有的同一份内容，并标注「N 人命中相似内容」作为共识信号（权重提升，≈部门共识答案）；综合分 = 归一化 BM25（按各节点索引规模归一化，防「文档多的人永远赢」）+ 命中词覆盖度 + 共识人数。
- L3 分档与展示截断：高相关 / 中相关 / 低相关（折叠为「低相关 N 条」）；展示取 top 30-50。
- L4 AI 上下文预算：给 LLM 的上下文是**预算制、与节点数无关**——默认 8K token 预算（可配），按综合分贪心装入片段（每条 = 标题 + 出处 + 约 300 字片段 ≈ 250-350 token），约 25-35 条后停止。无论多少节点返回，进入模型的最优片段条数恒定，不会打爆。若需更全覆盖，可升级 map-reduce 分批摘要再汇总（v1 不做）。预算上限与所配模型挂钩：DeepSeek 现为 1M 上下文（调研 03），可调大预算换取更全综合，但成本与延迟随之上升，默认仍 8K。

**千人级聚合分层**（§15.4 演进项之一）：按组先聚合（组内 top-10）再跨组汇总，把消息量从 1000 条降到 组数×10 条；100 人规模不需要。

**多会话（支持）**：
- 随手问：每次提问即一个会话（qid），支持并发多会话；历史提问列表可回看；「追问」默认基于当前会话已聚合的结果继续（不重新广播），可手动「重新搜索」再广播。
- AI 问答：完整多会话——左侧会话列表，每会话独立上下文（系统提示 + 历史对话 + 当轮检索片段），本地 SQLite 存储，可切换/重命名/删除。

### 15.6 笔记分组、提问组与会话语义澄清（第四轮反馈落案）

**随手记笔记分组**（本地组织维度）：
- 支持自定义分组（如「数据库」「项目X」），把挂载的目录/文件/笔记归入分组（一个来源可属多个分组）；
- 分组用于：侧边栏按组筛选与统计、批量管理（整组排除/暂停共享）、快速定位；
- 预留：分组与「提问组」的可见性联动（将来可实现「某组笔记只对某提问组可见」），v1 不绑定（排除规则已是可见性控制）。

**提问组（广播域维度，用户提议采纳）**：
- 每个人可加入一个或多个组（如「数据库组」「平台组」），另有默认的「全员组」；
- 提问默认只广播到提问者所在组（避免打扰与信息干扰）；提问时可选择指定组/多组/全员；
- 组管理轻量方案：自由建组 + 自由加入（去中心化，符合部门工具气质），组清单经 relay 同步；
- **已实现（v0.6.3）**：组有名称 + 描述（所有人可见）；任意人在设置页建组；加入/退出 = 勾选/取消并保存；relay 持久化组注册表（relay-groups.json）；管理员的邀请命令见 docs/design/m6-setup-and-invite.md；
- 实现时机：M4 即做（subject 已预留 chisel.query.<group>.broadcast，成本低）；100 人规模可先用全员组，千人级靠组隔离广播域；
- 附加：节点「静默模式」开关（暂不接收任何广播），进一步控打扰。

**会话语义澄清（随手问 vs AI 聊天）**：
- 两者不同。AI 聊天（DeepSeek 等）的「会话」= 持续多轮对话，点加号 = 另起一段全新对话；
- 随手问的「会话（qid）」= 一次广播提问的技术标识：结果回传、进度跟踪、历史记录都挂在 qid 上，对应「一条提问记录 + 它的结果集」，不是聊天多轮；
- 衔接设计：对某条提问结果「追问」时，若配置了 AI，追问链形成多轮上下文（基于该提问聚合的片段 + 历史追问）——体验接近 AI 会话；「重新搜索」则再次广播；
- AI 问答入口：完整复刻「点加号开新会话」体验（会话列表、多轮、独立上下文），与随手问是两个入口、两种心智，底层共享检索与 LLM 能力。
